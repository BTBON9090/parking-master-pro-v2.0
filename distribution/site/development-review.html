02 / SIZE AUDIT先把计量口径对齐

我们的游戏，到底有多大？

核心是 React + TypeScript 界面、Three.js / WebGL2 画面，以及 cannon-es 与自定义车辆逻辑。地图大量通过程序生成和重复资源组合；客户端不依赖在线游戏服务器或模型 API 完成驾驶。

对象本次测得它代表什么
网页资源 dist35.31 MB98 个文件；不是首屏一定全部下载的流量。
Android APK26.99 MB压缩后的安装包。系统 WebView 承担网页运行环境。
Mac Apple Silicon DMG164.49 MB除游戏外，还包含 Electron 所需运行环境。
Mac Intel DMG168.74 MB另一架构的独立分发包，不应与上一行相加。
Windows x64 安装器153.71 MB压缩安装器；不等于安装后的 .exe 或整个应用目录。
iOS 工程 ZIP25.21 MB是源码工程包，不是 IPA。目前无法据此报告 App Store 下载大小。

桌面包明显更大，主要与运行时和封装有关；并不表示桌面画质自动更高。iOS 使用 Capacitor / WKWebView，实际大小需归档、签名后通过 Xcode 体积报告和 App Store Connect 核实。[1][2]

03 / WHY GIGABYTES体积、内存、帧率是三个指标

App Store 上的几个 G，
通常装的是什么？

大型写实游戏往往有更多独立美术资源、地图区域、语音、过场动画和长期追加内容。App Store 里也有很多小体积游戏；“大游戏”的体积不能代表所有商业游戏的门槛。

主要来源为什么会变大我们当前的选择
贴图与材质每件资产可有颜色、法线、粗糙度等多张贴图，还需要不同细节版本。大量纯色、低复杂度材质和资源复用，独立高清纹理少。
模型与场景大地图、精细内饰、角色动画、破坏模型和多个细节层级会累积。风格化低面数车体、程序化道路与重复建筑部件。
音频与视频多语言配音、音乐、长视频、不同转速与负载的声音素材。11 个随包音频文件，结合代码驱动声音；素材量较少。
引擎与平台运行库、插件、着色器及平台资源；与实际封装方式有关。移动端借助系统 WebView，桌面端自带 Electron。
后续下载与缓存首次进入再下载地图、皮肤、语音；“App 大小”与“文稿与数据”分开增长。目前主要资源随包提供，无大型内容下载系统。

四个数字必须分别看

  1. 下载大小：玩家耗费多少流量

    受压缩、设备分片、增量更新和下载哪些内容影响。

  2. 安装占用：设备磁盘上留了多少文件

    包括解压文件；后续资源、存档和缓存可能继续增加。Apple 的分片会让不同设备拿到不同包。[1]

  3. 运行内存：资源展开后占多少 RAM / 显存

    一张压缩图片文件很小，解码和上传 GPU 后却可能很大。

  4. 帧时间：每一帧需要多少 CPU / GPU 工作

    和镜面次数、阴影、像素量、物理计算、提交次数相关，不能从包体推出。

示意：2048 × 2048 × 4 字节 = 16 MiB
同一张未压缩 RGBA8 纹理，完整 mip 层级约 21.3 MiB。
升到 4096 × 4096：基础层 64 MiB，含 mip 约 85.3 MiB。

这是未压缩 GPU 纹理的算术示例，不是本项目的显存实测；GPU 压缩格式会改变占用。它说明“文件压得小”和“运行时省内存”需要分别优化。

体积变大只有在换来玩家能感知的价值时才值得。一套好的发动机声音、一致的光照、清晰的轮胎接地关系，往往比把所有贴图升到 4K 更有意义。

04 / PRODUCT GAP依据项目现状，不给虚假的综合评分

我们已经有什么，
距离成熟产品还差什么？

对比对象是完成度较高的商业驾驶游戏，而非假定每款大体积游戏都更好。以下区分代码事实、历史验证和产品判断；本次没有重跑完整实驾验收。

维度已具备的基础差距 / 下一项证据
驾驶与物理挡位、刹车、悬架、翻滚、挂车、质量碰撞与事故恢复；有自动回归。风格化游戏标定，不是厂家级或工业级仿真。需真机驾驶反馈与异常路况复测。
内容与玩法22 车、9 地图入口、训练考核、挑战路线与地图编辑。数量不等于耐玩。应验证新手是否理解目标、任务是否有节奏、失败是否可解释。
视觉Blender 车辆、驾驶舱、后视镜、阴影、事故表现。当前图像呈明显低多边形风格；材质层次、近景细节、环境丰富度和整体美术一致性有提升空间。
音效与反馈启动 / 停机、怠速 / 负载、路面和碰撞声音；车库试听。不同动力类型的辨识度、循环接缝、音量混合、手机扬声器听感要继续打磨。
性能与适配画质档位、动态分辨率、部分实例化、资源释放与空间索引。缺手机持续性能矩阵。浏览器触控布局通过，不代表手机温升、电耗、内存和帧率通过。
商业完成度跨平台打包、下载清单、Android 签名连续性有记录。Mac / Windows 未签名；iOS 无 IPA。此次查看的业务代码与依赖未见完整内购、订单、云存档或运营体系。
工程维护类型检查与丰富回归测试；已有资产制作脚本。GameCanvas3D.tsx 约 3,786 行，职责集中；README 的车 / 图数量滞后。后续修改需控制回归范围。
最应避免的误判

测试脚本通过 ≠ 所有设备体验合格。新增重车 8,000 三角面以内 ≠ 渲染便宜：US22 资产记录仍有 182 个 mesh、17 种材质，镜面和阴影还会增加渲染工作。

本地依据：E3 当前代码与配置；E4 round31 验收与资产统计。旧 round21 中出现过较大帧时间波动，但不能直接当成当前版本成绩。

05 / PERFORMANCE先测量，再决定优化对象

性能优化：先保住驾驶的连续性。

当前已有优化应保留并建立回归。新的工作重点是定位长帧与热降频，把最差场景纳入验证，而不是只看空旷道路的平均 FPS。

优先级具体工作怎么证明有效
P0 · 建立基线固定机型、分辨率、画质、路线与车辆；记录 CPU / GPU 耗时、p95 / p99 帧时间、内存、加载和输入延迟。相同场景优化前后比较，记录分辨率变化；不可仅靠自动降清晰度宣布成功。
P1 · 多次渲染分析三面镜子、俯瞰图、阴影的成本；按可见性 / 距离裁剪，试验镜面分时更新与缓存。掉头、倒车、挂车转弯仍能准确判断位置；镜面降频不造成驾驶误导。
P1 · 场景提交继续合并 / 实例化重复车辆与建筑，减少材质切换；给远处物体添加 LOD 或简化显示。实际 draw calls、可见三角面、渲染提交时间下降，车门 / 轮胎动画与碰撞不受破坏。
P1 · CPU 与物理剖析碰撞候选、道路查询、NPC 更新；减少帧循环内创建对象，固定物理步长并合理插值。30 / 60 / 120 Hz 的行驶结果一致；低帧率不能穿墙或改变刹车距离。
P2 · 资源与加载按场景加载，拆分编辑器等非首屏代码；缩略图改尺寸 / 压缩；大 GLB 比较压缩和解码成本。冷启动、资源峰值与卡顿改善；弱网 / 加载失败可恢复，不黑屏。
P2 · 生命周期反复换车换图、切后台、锁屏、音频中断、WebGL 上下文丢失及恢复。内存没有持续上涨，松开触控后输入归零，恢复后车辆和声音状态正确。

一套适合本项目的验收目标 建议，尚未达标认证

手机最低支持档

固定目标机型与画质，先以持续 30 FPS 为底线；热机路线 p95 帧时间 ≤ 40 ms，p99 ≤ 66.7 ms。标注测试中实际分辨率，不能靠持续模糊画面过关。

桌面 / 较强手机档

以 60 FPS 为目标；p95 ≤ 20 ms，p99 ≤ 33.3 ms。若设备不满足，明确推荐档位，不做全设备 60 FPS 承诺。

  • 每轮至少包含：拥挤高速、地下车库、多镜面驾驶舱、事故碎片与最大车辆；各跑同一段路线。
  • 连续驾驶 20 分钟，记录首 5 分钟与末 5 分钟差异；设备温度、电量和后台应用条件保持可比。
  • 换图 / 换车 20 次观察内存趋势；成功加载后不出现持续增长或明显卡住。
  • 第一轮用手边设备确定基线，再补目标用户的中低端手机；没有测过的系统列为待验证。

包体优化和帧率优化要分别记账。主 JS 当前约 1.65 MB，单独 gzip 后约 0.49 MB；拆包主要改善加载与解析，不会自动解决每帧镜面、阴影和物理成本。

本地依据：E3 renderQuality.ts、GameCanvas3D.tsx、sceneBuilder.ts；E5 当前主 JS 的 gzip 测量。所有目标为建议验收线，不是本次测得性能。

06 / VISUAL DIRECTION用一致性提高完成度

画质升级，先做“精致风格化”。

个人开发者最可控的路线，是保持现在的轻量几何，提升车身比例、倒角与法线、材质粗糙度、接触阴影、色彩和环境构图。单纯加面数和 4K 纹理，很容易同时增加制作与适配负担。

  1. 第一层：读得清，接得住

    统一车身 / 玻璃 / 轮胎材质，改善轮胎接地与驾驶舱近景；校准曝光和色调，让道路、障碍和可行驶边界更易分辨。

  2. 第二层：用有限素材建立质感

    道路和内饰优先使用少量高复用 PBR 贴图、法线与细节贴花。静态环境可试烘焙光照 / AO；移动物体继续使用合理的动态光影。

  3. 第三层：按设备分配画质预算

    近景精细、远景简化；高档允许更好的阴影与环境反射，手机低档减少后处理和透明叠加。保持玩法与可读性一致。

  4. 第四层：声音与运动一起升级

    改善转速 / 负载声音混合、碰撞层次、轮胎反馈和镜头稳定性。让游戏“更像在开车”，不只让截图更漂亮。

样板验收流程：选择 2 辆代表车 + 1 张代表地图 → 固定镜头做升级前后截图 → Blender 渲染检查 → 独立游戏内检查 → 同设备性能对比 → 再推广到全车队。公开车型参数与模拟调校继续分别注明。

贴图可评估 KTX2 / Basis 等 GPU 压缩，需验证解码、兼容性、清晰度与显存收益；模型压缩也应同时衡量加载解码成本。不要把一种格式当成无条件提速按钮。[3]

要不要换成 Unity / Godot / Unreal？

路线本项目适用判断代价与触发条件
继续 Three.js + Capacitor当前优先。保留既有玩法、测试、网页分发与跨端基础。需要自己维护资产、性能工具与原生插件接口；先完成手机性能基线。
局部增强现有架构把物理、输入、音频、渲染逐步分离；必要时接入原生能力或评估 Worker / WASM。数据同步也有开销。一次拆一个边界，跟随具体瓶颈，不做无目标重构。
做引擎迁移样机只有在明确需要复杂渲染、成熟编辑流程或 WebView 达不到目标时再比较。先移植一车一图做相同设备 A/B；引擎不等于更高画质，迁移会消耗数周至数月。
直接追写实开放世界短期不适合单人承担完整制作与运营。核心瓶颈是持续资产生产、平台验证和资金，而非下载一个更强的引擎。

时间为规划判断，取决于目标范围与可投入工时；迁移前再核对目标引擎当时的许可和商业条款。本次没有做各引擎性能比较。

07 / TRUST & RELEASE保护玩家、收入与作品权利

安全和商业发行，
需要按阶段补齐。

已核对 Electron 已关闭 Node 集成，启用上下文隔离、沙箱和 Web 安全，并对外链设白名单；Android 配置禁止混合内容。本次 npm audit --omit=dev 返回 0 个已知生产依赖漏洞。这不是完整安全审计，也不覆盖 Electron 开发依赖中的运行时风险。[4]

阶段应该完成为什么值得做
现在：本地单机完善 CSP 与资源来源限制；地图导入做结构、数值、数量和文件大小校验；更新依赖；备份存档与签名密钥，密钥不入仓库、不随包发布。导入入口可见 JSON 解析和类型断言，未见入口处完整运行时校验 / 大小限制；先防无效数据导致卡死或损坏，不把它未经复现地称为可执行代码漏洞。
对外发行Mac 签名与公证、Windows 签名方案评估；HTTPS、清晰版本号、可信下载源；发布材料和二进制一致。降低系统拦截与仿冒分发风险。SHA-256 能核对文件，但同站点可被同时篡改时不能替代可信签名。
增加付费原生商店交易验证、恢复购买、退款撤销、离线权益；如有服务端，保证订单幂等与审计。localStorage.paid = true 不是可靠付费系统。纯客户端无法彻底防修改。
增加账号 / 排行榜服务端验证权限与得分，限流、备份、删除账号与数据；限制日志中的个人信息。把“客户端声称得了多少分”当作输入。实时多人还需要权威服务器、同步与持续运维。

支付私钥、服务器密钥不能放在 JS 或客户端包中；混淆和本地加密不能让内置密钥保密。离线单机允许玩家自娱修改时，不必先投入昂贵反作弊；涉及付费、跨端权益或公开排名时再建立可信验证边界。

权利与隐私：现在就能明确的边界

  • 车标素材的 CC0 许可，不等于品牌方授权。项目使用真实车名、品牌 SVG 和车型外观；商业版应逐项审查商标、设计、素材及营销呈现。可优先制作原创车型、名称和标识；仅改名未必解决外观权利问题。必要时让知识产权专业人士判断。[5]
  • 建一份资产台账。记录模型、音频、字体、图标来源、许可、署名、购买凭证和可商用范围；AI 或程序生成内容也保留制作记录。
  • 单机不等于没有网络数据。现有网页入口含 Google Fonts，更新检查访问远端清单 / GitHub；应盘点真实网络请求、服务商日志与新增 SDK，再填写隐私披露。[6]
  • 如加入广告，按实际跨公司跟踪 / IDFA 使用判断 ATT；不是“只要联网或做统计就一定弹 ATT”。优先避免不必要跟踪，减少账号与敏感信息。[7]

发行路径必须先选市场

中国大陆

Apple 的大陆上架说明要求游戏提供批准号及支持材料；APP 备案、游戏审批、运营资质是不同事项。NPPA 申报流程涉及有资质的出版单位，说明也包含网页、网络下载的单机游戏，不能默认“单机 / 免费”豁免。你需与合适的出版发行合作方及专业顾问确认具体路径、主体和适用义务。[8][9][10]

其他国家与地区

可先选择具体市场评估上架，仍需满足当地隐私、消费者、年龄分级、税务和 IP 要求。完整可玩的 WebView 游戏有机会通过审核，但“打包网页”本身不保证合格；需证明持续娱乐价值和设备体验。[5]

以上是发行准备判断，不替代针对本产品的法律意见。市场、收费方式、联网能力和目标人群确定后，应由专业人员核定，包括适用的未成年人保护 / 实名防沉迷要求。

08 / BUSINESS MODEL先有付费理由，再接支付

优先验证一次性付费，
不要先背上持续运营的负担。

可先在合适的测试范围提供完整试玩闭环：学会起步 → 完成一个有趣挑战 → 看懂成绩 → 愿意再试。验证后，采用免费试玩 + 一次性完整内容解锁，或直接买断。具体价格先测试，不由包体大小决定。

模式适合程度条件与代价
买断 / 一次性解锁优先验证承诺明确、维护边界较清楚；要有足够内容、恢复购买和稳定品质。试玩解锁比纯买断多一条内购链路。
独立扩展包后续可做新挑战、原创车辆主题包；不要把修复、正常操控或安全设置做成收费项目。
自愿激励广告有用户后评估广告收入依赖活跃、地区和填充；SDK 带来隐私、性能、审核和体验成本，低流量收益可能很有限。
订阅 / 通行证暂不推荐玩家会期待持续内容和服务，单人需要承担稳定交付压力。
驾校 / 展示定制少量试点可以卖场景定制与部署服务；销售、交付支持需你投入。不可宣传未经认证的训练效果。
多人、交易、抽卡先不投入后端、反作弊、客服、经济系统与合规复杂度会显著上升。

App Store 内数字内容解锁按适用商店规则设计，默认采用 IAP；地区例外不能跨市场照搬。实现时包括恢复购买与退款 / 撤销处理。[5][11]

没有证据表明回访与付费能覆盖获客成本前，不扩大买量。商店截图、短视频与驾驶手感需要一致；不要用宣传画质替代实际运行画面。

首个验证周期的可控现金计划

单机也可能产生流量账单

当前 Android 包约 27 MB，假设 10,000 次完整下载，仅安装包就约 270 GB 出站流量，尚未计更新、重试和其他平台。CPU 计算发生在玩家设备上，不等于分发成本永远为零。

内容分发成本 ≈ 实际出站 GB × 服务单价 + 请求 / 存储费用
新增在线功能后，再增加数据库、验证、日志、备份与维护费用。

比纯现金更容易被忽略的是时间：每周若有 10–15 小时可投入，12 周就是 120–180 小时。这部分即使不付工资，也要算进机会成本和可承诺的更新节奏。

两辆车、一张图、一次完整新手体验

先验证发行可行，再做支付闭环

第 10–12 周受控发行

小范围推出，用反馈决定下一步
